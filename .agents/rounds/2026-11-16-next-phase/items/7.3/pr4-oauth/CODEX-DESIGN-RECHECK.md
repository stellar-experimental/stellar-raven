# PR 4 OAuth design revision 2 — security recheck

**Verdict: design PASS.** Findings 1–3 are resolved soundly at the design level. No new blocker or major security problem found. Reconcile the minor items below during implementation. This is not implementation approval; the owner decisions and required diff review remain.

Reviewer: Codex frontier, independent read-only lane, 2026-11-18. Scope: revision 2 against the prior Codex/Fable reviews, current server/auth code and auth tests, and newly npm-packed oauth-provider 1.2.4 source/declarations. Migration guidance fetched with `gh api repos/cloudflare/workers-oauth-provider/contents/docs/migration-1.x.md`.

1. **note — Earlier blockers resolved. File: DESIGN.md:58–75, :114–136.** The explicit `{ ...env, OAUTH_PROVIDER: undefined }` copy removes even an already-populated outer helper; applying it to both dispatch paths avoids shared mutation. The exact `request.url` origin selection and pre-login 404 close the unknown-issuer fallback. The named native allowlist, both authorization legs, error redirects and parked `completeCallback` check close the callback-policy gap. Put the parked check after state/binding validation and before the WorkOS exchange, preserving state consumption and cookie cleanup. **Fix:** implement the stated boundaries, including placing origin selection before `/playground/login` can initiate browser login. Concurrent A/B/A probes with explicit and omitted resources and a contaminated outer env passed.

2. **minor — Migration exception ends at token expiry, not first refresh. File: DESIGN.md:79–82, :249, :309.** “Until then” and “until bound” still imply that binding the grant stops its old token working elsewhere. Reproduced: refresh the unbound grant on .org; its old access token still gets 200 on .buzz, while the replacement gets 401. The provider resolves each old token's absent audience independently. **Fix:** state that existing audience-free access tokens remain usable across the three trusted origins until expiry, including after refresh. Qualify the cross-host rejection harness assertion as applying to bound tokens/grants, and retain an explicit old-token-after-refresh case.

3. **minor — The loopback host set is not a small cache bound. File: DESIGN.md:50–52.** Three HTTP host spellings with arbitrary valid ports permit roughly 196,000 distinct origins. That is finite, but a plain persistent Map is unnecessarily large for development. This is not a demonstrated production attack: the deployed routes are the three fixed HTTPS origins. **Fix:** avoid caching loopback providers, or set a small explicit cache limit with eviction. Keep production providers at module scope and preserve the narrower bypass host set.

4. **minor — Make the changed policy's regression cases explicit. File: DESIGN.md:225–234.** The plan omits explicit CIMD and legacy-client variants requested by the original review, and the successful Cursor registration case contains only allowed schemes. **Fix:** add a mixed registration such as HTTPS plus `smb:` that registers but whose `smb:` authorization returns local 400 on both legs/error paths; cover CIMD and a seeded legacy registration too. State that spoofed forwarding/Host headers are ignored: an allowed request URL still works, and an unknown request URL still gets 404 despite an allowed-looking header. The current “spoofed … give 404” wording is ambiguous.

5. **note — Registration, logging, D5 and rollback are acceptable. File: DESIGN.md:124–131, :178–219.** “At least one allowed URI” is safe because authorization checks the selected URI, including CIMD and parked requests. The prototype returned 400 for smb-only, 201 for HTTPS+smb, 400 for HTTPS+remote HTTP, and 201 for claude-only. Replace “stops probe-only registrations” with “rejects registrations with no usable callback”: adding HTTPS trivially satisfies it. The scheme log is acceptable if derived from parsed `URL.protocol`, colon removed, then validated by the specified length/character rule; never log the full URI or use the token as proof of legitimate client demand. D5 now correctly records the supplied-redirect, implied-refresh and CIMD replacement exceptions, with real token-endpoint tests planned. Rollback records storage compatibility, the private-key client limitation, loss of security checks, and no KV rollback; exact deployed-artifact confirmation appropriately remains with the orchestrator.
