**Verified classification defect for one repository.** The same Scout response returned `codeVerified.isDeployableContract: true`, `repoMeta.kind: contract`, and `repoMeta.kindBasis: isDeployableContract`. The independent `scout.searchRepos` result agreed. Its scan used the same `430a28e` ref.

The [Horizon README at that ref](https://github.com/stellar/stellar-horizon/blob/430a28e79b3b43c213840e45523519ca11251c0a/README.md) calls Horizon an API server. It describes the server between Stellar Core and applications. The source tree puts every Rust `Cargo.toml` and `.rs` file under `internal/integration/contracts/`. The [workspace manifest](https://github.com/stellar/stellar-horizon/blob/430a28e79b3b43c213840e45523519ca11251c0a/internal/integration/contracts/Cargo.toml) lists six test contracts. The [testing guide](https://github.com/stellar/stellar-horizon/blob/430a28e79b3b43c213840e45523519ca11251c0a/internal/docs/TESTING_NOTES.md) places them in the integration test area. The returned `IncrementContract.increment()` symbol comes from the [integration fixture](https://github.com/stellar/stellar-horizon/blob/430a28e79b3b43c213840e45523519ca11251c0a/internal/integration/contracts/increment/src/lib.rs).

The [live Scout OpenAPI](https://stellarlight.xyz/api/openapi.json), version `1.9.54`, defines `isDeployableContract` as the repository's product. It excludes platform, SDK, and tooling repositories with fixture crates. The schema derives `kind: contract` from that flag before the project link. Horizon therefore gets a false contract label because test fixtures are treated as its product.

Use the new `sls-088` identity. The [retired `sls-046` receipt](../../../improvements/resolved.json) covers `stellar/stellar-core`, not Horizon. Its [merged upstream PR #498](https://github.com/Stellar-Light/stellarlight/pull/498) added known-infrastructure exclusions and product semantics.
