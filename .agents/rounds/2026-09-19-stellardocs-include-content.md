## Defect

Ten stellarDocs search operations declare `includeContent`. Only `stellarDocs.search_docs` mapped it
(`conditionalParams["includeContent=true"]` adds `content` to Algolia `attributesToRetrieve`). On
`search_docs_in_category`, the seven category operations, and `search_meeting_notes` the argument
passed schema validation and did nothing. The caller got 20-word snippets and no error.
`get_doc_page_sections` handles the parameter in adapter code and was never affected.

Observed impact, from 1,152 logged code-mode agent runs of an external harness against a local server
on `544e5d9d`: 484 of 1,713 successful `execute` scripts (28%) passed `includeContent: true` to one of
the nine unwired operations; 430 runs (37%) were affected.

## Change

- `specs/stellar-docs.json`: the `search_docs` mapping on the nine operations; `content?` in their
  `returns` text; the size warning that `search_docs` already carries on the parameter.
- `catalog/manifest.json`, `specs/super-spec.json`: regenerated by their scripts.
- `test/adapters.test.ts`: enumerates every operation that advertises the parameter from the manifest.
  The stub returns only the attributes a request names. Asserts no `content` without the flag and
  `content` with it. Nine tests fail against the `544e5d9d` manifest; `search_docs` passes on both.

Design note: the eight client-filtered operations over-fetch 100 hits, so `includeContent: true` now
retrieves `content` for 100 hits and returns at most 20. Live latency was unchanged in a nine-operation
probe (about 90 to 600 ms on both builds, same hits in the same order). A two-pass design (filter
first, then fetch `content` for the kept hits) would cut the upstream payload; it is not needed for
correctness and is left as a follow-up.
